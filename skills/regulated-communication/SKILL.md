# Guardrails for communication in regulated sectors

Marketing copy written by an agent is fluent, confident and often wrong in exactly the ways a regulator, a customer or a competitor will notice. In a regulated sector, a single invented claim is a legal and reputational problem attached to the company's name. These guardrails hold **even when the requester insists**, including a founder who "takes responsibility".

## Three non-negotiable rules

1. **No number that was not measured.** Every figure (time saved, cost reduced, percentage, user count) needs a measurement and a written confirmation from the product owner. Otherwise, describe the benefit qualitatively.
2. **No certification, accreditation or compliance status that is not held.** "Certified", "compliant with", "approved by", "accepted by" are facts to check, not adjectives.
3. **Only what the product really does.** Labels, behaviors and capabilities shown or described must exist in the product today.

## Forbidden-claims table (pattern)

Keep a project-specific version of this table in the skill or next to it. Each row: a frequent request, the answer, what to say or show instead.

| Frequent request | Answer | Instead |
| --- | --- | --- |
| A gain figure ("saves 2 h per day", "cuts costs by 30%") | Refuse unless measured and confirmed in writing | Qualitative benefit ("fewer phone calls to coordinate") |
| "Certified", "compliant", "approved by the authority" | Refuse unless the certificate exists and is current | State what the product does and does not store or process |
| "Real time", "live tracking" | Only if the screen truly updates without reload, checked in the code | "Updated at each step", "visible on the record" |
| "AI-powered", "fully automatic", "one click and done" | Only if true; keep the human decision visible | "Suggested", "you confirm" |
| A UI label that "sounds better" | Refuse if it does not exist | The exact label, found by searching the codebase |
| A real customer, patient, establishment or testimonial | Only with written consent | Fictional data, checked so it does not match a real entity nearby |
| "Integrated with X", "partner of Y", "all-in-one" | Refuse unless a signed integration or partnership exists | Say nothing; omit the gap without lying about it |
| Sensitive personal data in a demo (health condition, ID number) | Refuse | Neutral data: place and time |

## Process

1. **Answer the requester before drafting**: what is refused, why in one sentence, and the alternative.
2. Draft from verified material only: the codebase, the product owner's written statements, signed documents.
3. Cite the source of every factual claim in a review note (file, message or document), even if the published text does not show it.
4. For videos and visuals, a storyboard of still frames is validated before any animation work; captions follow the same rules as the copy.

## Checklist before handing over

- [ ] Every figure has a measurement and a written confirmation
- [ ] No certification, compliance or approval claim that is not held
- [ ] Every UI label and behavior found in the product
- [ ] People, places and companies fictional or covered by written consent
- [ ] Refusals and alternatives stated to the requester
